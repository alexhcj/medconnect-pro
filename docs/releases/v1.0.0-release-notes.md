## Release overview

MedConnect Pro **1.0.0** is the first stable release of the feature-complete synthetic demo,
hosted on **Render**. It is a portfolio and interview demonstration of healthcare-oriented SaaS
engineering. It is **not** a deployed healthcare service, it is **not** HIPAA certified or HIPAA
compliant, and it is **not** hosted on AWS. Production hosting on AWS is a later 1.x release.

- Version: `1.0.0` (root `package.json`; [ADR-007](../decisions/ADR-007-semantic-versioning.md))
- Application: https://medconnectpro.app
- Marketing site: https://marketing.medconnectpro.app
- API health: https://api.medconnectpro.app/health

## Product / feature scope

Shipped milestones **M0–M8** and **M10–M21**. M9 (AWS hosting) is coded as infrastructure but
paused until an AWS account exists.

- M0–M7: repository and docs, mock identity and roles, patients, appointments and calendar,
  clinical records and audit model, appointment-linked telehealth sessions, billing, practice
  administration and audit viewer
- M8: public marketing site
- M10: live dashboard overview, in-app notifications, practice role assignment
- M11: HttpOnly cookie sessions, labeled mock MFA, security events
- M12: Daily call-object media on the telehealth session shell (when `DAILY_API_KEY` is set)
- M13: demo record-payment and labeled claims envelopes (not hosted Stripe or EDI 837)
- M14: demo OAuth / OIDC with PKCE and external identities (provider sign-in is off on the public
  demo)
- M15: API rate limiting, 429 envelope and security headers
- M16: live telehealth workflow (join before mint, leave versus end, device check before joining)
- M17: security and compliance maturity (clinical read audit, concurrent sessions, authorization
  matrix)
- M18: interview demo readiness on Render (demo accounts panel, participant entry, presentation
  pack)
- M19: paged and bounded lists, billing design parity
- M20: manual Render PR previews for the marketing site and web app; `main` deploys after `ci`
- M21: marketing and web app design refresh (homepage, `/about` roadmap board, `/architecture`,
  form surfaces, US date format with an accessible date picker, one-tap demo account picker)

Not in this release: production OAuth or MFA, in-session chat or recording, hosted payments,
claims submission, Redis, AWS production hosting, or HIPAA certification.

## Frontend

- Next.js App Router in `apps/web` (React, TypeScript, TanStack Query, React Hook Form + Zod,
  Tailwind CSS, Headless UI)
- Static marketing site in `apps/marketing` (Next.js static export)
- Mock-first local scripts plus `dev:real` against Nest
- Frontend role and navigation checks are UX only; Nest authorization is authoritative

## Backend

- Modular NestJS 12 API in `apps/api` (TypeScript)
- Server-side authentication, RBAC, tenant isolation, resource authorization and audit events
- One Nest application, not microservices

## API

- REST with generated OpenAPI (`npm run openapi:generate`)
- Swagger UI is off on the public demo (`/api/docs` returns 404); hiding it is not a security
  control

## Database

- PostgreSQL with TypeORM and row-level security on tenant-owned tables
- Runtime role `medconnect_app`; migrations and seed use the table owner
- The public demo uses one Render Free Postgres database with synthetic data only

## Security

This release demonstrates healthcare-oriented engineering patterns. It is **not** a compliance
certification.

Implemented in the demo: RBAC and resource-level authorization, tenant isolation including
PostgreSQL RLS, audit logging, document ACL, least-privilege database role, rate limiting,
security headers, and secrets outside source control. Frontend checks are not authorization. The
API never trusts a browser-supplied tenant id.

## Authentication

Identity is a **mock IdP**: email and password, Nest HttpOnly session cookies, refresh-token
rotation, idle and absolute expiry, and a labeled mock MFA challenge (not production TOTP). The
demo OAuth / OIDC integration is not a production IdP and is off on the public demo. Production
OAuth 2.0 / OpenID Connect and production MFA remain the target in
[ADR-003](../decisions/ADR-003-authentication.md). See [docs/security/](../security/README.md).

## Known limitations

- **Not HIPAA certified or HIPAA compliant.** Engineering patterns are not a formal assessment.
- **Free hosting.** Free web services sleep after about 15 minutes without traffic, so the first
  request can take up to a minute. The `/login` page shows the API status and can wake it.
- **Database expiry.** The Free Postgres database expires on 2026-11-13 unless the operator
  upgrades or replaces it. It has no platform backups.
- **Uploads are temporary.** Uploaded documents are lost when the API sleeps, restarts or
  redeploys.
- **Telehealth media** works only when the operator has set `DAILY_API_KEY`; otherwise the session
  shell says media is unavailable. Chat and recording are not in the demo.
- **Provider sign-in** is not configured on the public demo; use the demo accounts.
- **No hosted payments or claims submission.** Payment and claims UI are labeled boundaries.
- **No AWS production.** AWS hosting is paused until an account exists.

## Demo-data / no-PHI statement

All data is **synthetic** ([ADR-005](../decisions/ADR-005-synthetic-demo-data.md)). Patient names,
addresses, dates of birth, identifiers, conditions, medications, appointments, invoices and audit
fixtures are fictional. The demo database must never contain real PHI, real credentials or real
clinical records.

## Rollback considerations

From `docs/workflows/deploy-render.md`:

- A red `ci` on `main` deploys nothing.
- Roll back one service in the Render dashboard to its previous successful deploy; a marketing
  rollback does not affect the application or API.
- Migrations are forward-only for the demo: fix the schema forward or restore a dump into a
  replacement database. Do not run `migration:revert` as part of an API rollback.
